- # How To Measure Performance
	- ## Overview
		- Measure how fast `lsg` builds a garden, how fast its pages and search respond next to Logseq's build, and record the results that later changes compare against. The page loads, feature timings and search go to [[lsg/Ref/Logseq Compatibility/Performance]]; build times go to [[lsg/Ref/Publication Speed]].
	- ## Prerequisites
		- A run directory from `mise run parity:build` and `mise run parity:compare`, as [[lsg/How To/Compare a Build with Logseq]] shows. `parity:compare` extracts Logseq's build beside the `lsg` build.
		- Playwright's Chromium, which the tasks install through `uv` on first use.
	- ## Steps
		- ### 1. See where a build spends its time
			- Add `--timings` to any `lsg publish` command:
			- ```text
			  lsg publish --graph <garden> --output <site> --filename-format triple-lowbar --include <namespace> --timings
			  ```
			- The last line of stderr lists each phase in milliseconds, after any diagnostics. With `--format json`, the report gains `timings`, a list of `phase` and `ms`, and `total_ms`. Without the flag, the output is unchanged; with it, the published files are the same. Rust callers read the same phases from `SiteReport::timings`, and `garden::load_garden_timed` times the `read` and `parse` phases of any garden load. [[lsg/Ref/Publication Speed]] says what each phase covers.
		- ### 2. Time a whole build
			- Run the publication benchmark:
			- ```sh
			  mise run parity:publish-bench --corpus all
			  ```
			- `--corpus` chooses `gitpa-sized` (the default), `encode-garden` or `all`. The encode garden comes from `ghq` unless `--garden <path>` names another checkout. `--runs` sets the number of warm builds. `--output <file>` writes the rows as JSON, and `--record` appends them to [`docs/parity/publication-speed.json`](https://github.com/codekiln/logseq-gardener/blob/main/docs/parity/publication-speed.json).
			- The `gitpa-sized` corpus is generated by [`scripts/parity/sample_garden.py`](https://github.com/codekiln/logseq-gardener/blob/main/scripts/parity/sample_garden.py) from a fixed seed. It has Gitpa's page count, word count, namespace depth and link, block and property density as of 2026-10-31. Pages must say `public:: true` to be published, as in Gitpa, and 25 are withheld. Every machine generates the same files; each row records their digest.
		- ### 3. Measure page loads in both builds
			- For a quick check, run `mise run parity:perf --profiles desktop --loads 1`, or pass `--fixtures <file>` with a shorter list of pages.
			- A full `mise run parity:perf` run takes hours, because Logseq's build needs minutes per load on the phone profile. It writes `perf.md` and `perf.json` into the run directory.
			- To measure one feature in the run's site, pass one of `--graph`, `--slides`, `--media`, `--sidebar`, `--queries`, `--flashcards` or `--plugins`. `--baseline-lsg <binary>` also times a whole-garden build with another `lsg`, such as one built before your change.
		- ### 4. Measure search
			- Measure search in a built site, beside Logseq's build when the site belongs to a parity run:
			- ```sh
			  mise run parity:build
			  mise run parity:compare   # extracts Logseq's gh-pages build beside the lsg build
			  mise run parity:perf --search-site target/parity/<run>/site --record
			  uv run --script experiments/pagefind/measure.py
			  ```
			- `parity:perf --search-site` fails while any `lsg` value is over its budget and names it. The last command measures Pagefind on the same build, for the comparison on [[lsg/Ref/Logseq Compatibility/Search Performance]].
		- ### 5. Record the results
			- Add `--record` to `parity:perf`. A full run rewrites [[lsg/Ref/Logseq Compatibility/Performance]], the committed results that compatibility pull requests compare against. A run with a feature flag replaces only that feature's section, and `--search-site` replaces the search sections and `docs/parity/search-performance.json`.
			- Add `--record` to `parity:publish-bench` to append its rows to `docs/parity/publication-speed.json`. [[lsg/Ref/Publication Speed]] says when the CI check needs new rows.
			- Commit the changed files with the change they measure.
	- ## Troubleshooting
		- If `parity:perf` stops with `Logseq build missing`, run `mise run parity:compare` for the run first.
		- If a value is bold in the results, it exceeds its budget in [`scripts/parity/budgets.toml`](https://github.com/codekiln/logseq-gardener/blob/main/scripts/parity/budgets.toml). Change the code, or change the budget in the proposal of the feature that needs it, with the measurements that justify it.
		- `mise run parity:budgets` checks the title index, shard and chunk budgets and the page sizes on the fixture garden in CI; [[lsg/Ref/Parity Tasks]] lists what else it checks.
