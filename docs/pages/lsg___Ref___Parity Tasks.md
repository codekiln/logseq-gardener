- # Parity Tasks
	- The `parity:` mise tasks in [`.mise/tasks/parity/`](https://github.com/codekiln/logseq-gardener/tree/main/.mise/tasks/parity) build the whole encode garden with `lsg`, compare it with Logseq's `gh-pages` build, and measure both. Their Python code is in [`scripts/parity/`](https://github.com/codekiln/logseq-gardener/tree/main/scripts/parity). [[lsg/How To/Compare a Build with Logseq]] shows them in order, and `mise run <task> --help` lists each task's flags.
	- ## The tasks
		- Every run writes into a new directory, `target/parity/<UTC time>/`. `parity:compare`, `parity:screenshots` and `parity:perf` use the latest run unless you pass `--run <directory>`.
		- | Task | Writes | What it does |
		  | --- | --- | --- |
		  | `parity:build` | `site/`, `settings.json`, `diagnostics.txt` | Builds a release `lsg` and publishes every page whose top-level namespace `lsg` can select, with `--journals` and `--search`. `settings.json` records the garden commit, the `lsg` version and commit, every option passed, and files whose namespace `lsg` cannot select. |
		  | `parity:compare` | `logseq/`, `report.md`, `report.json` | Extracts Logseq's build, reads its page list from `static/js/db.gz`, and lists pages present in one build and missing from the other. Logseq-only pages are grouped as journals, reference-only pages, pages hidden by `:hidden`, titles `lsg` cannot select, and other pages. Each other page needs an explanation or a fix. |
		  | `parity:screenshots` | `screenshots/index.html` | Captures every page in [`scripts/parity/fixtures.txt`](https://github.com/codekiln/logseq-gardener/blob/main/scripts/parity/fixtures.txt) from both builds at 1280 by 800 and at 390 by 844 (`--viewport desktop` or `phone` takes one) in light mode, after scrolling so Logseq draws its Linked References. The index shows the two captures side by side. |
		  | `parity:perf` | `perf.md`, `perf.json` | Loads each fixture page from both builds with an empty cache, on a desktop profile and on Lighthouse's mobile profile (four times CPU slowdown, 150 ms round trip, 1.6 Mbps). It records time until the page title is visible, first contentful paint, data and script transferred before the title, and peak JavaScript heap, then types the queries in [`scripts/parity/search-queries.txt`](https://github.com/codekiln/logseq-gardener/blob/main/scripts/parity/search-queries.txt) into each build's search. It scrolls each build's journals feed until it shows ten later batches and records the peak heap, and times `lsg publish` on the whole garden with the run's options, without `--journals` and without `--search`, each the fastest of three runs. Bold values exceed [`scripts/parity/budgets.toml`](https://github.com/codekiln/logseq-gardener/blob/main/scripts/parity/budgets.toml). `--record` rewrites [[lsg/Ref/Logseq Compatibility/Performance]]. |
		  | `parity:publish-bench` | rows on stdout, optionally in [`docs/parity/publication-speed.json`](https://github.com/codekiln/logseq-gardener/blob/main/docs/parity/publication-speed.json) | Publishes a generated Gitpa-sized garden and, with `--corpus all`, the whole encode garden, once cold and five times warm with `--timings`. It reports each corpus's times, phase times, peak memory and output size, and with `--check` compares them with the recorded rows. [[lsg/Ref/Publication Speed]] has the results and explains the CI check. |
		  | `parity:build-bench` | measurements on stdout, optionally as JSON with `--output` | Measures build plugins on a whole garden against the `[build_plugins]` budgets; the fastest of `--runs` builds per variant counts. |
		  | `parity:budgets` | nothing | Checks `lsg` page sizes on the fixture garden against the budgets; CI runs it, as described below. |
		- The local server compresses text files with gzip, as GitHub Pages does, so transfer sizes match the published sites.
	- ## The CI check
		- `mise run parity:budgets` runs in `mise run ci`. It publishes the fixture garden in [`tests/fixtures/parity-garden/`](https://github.com/codekiln/logseq-gardener/tree/main/tests/fixtures/parity-garden), then publishes it again with 2,000 added pages that nothing links to. It fails when a page's first-paint size or script size exceeds the budget, or when a page grows because the garden grew.
		- It also checks the `[shell]` budgets: `lsg-shell.js` and each page's header and sidebar markup must stay within their sizes and keep them when the garden grows.
		- It publishes the fixture garden once more with 1,000 older journals and checks the `[journals]` budget: `lsg-journals.js` stays within its size, and it and the home page keep their sizes.
		- The `[code]` budget limits the code and table styles every page carries and the growth of the largest fixture page with fenced code.
		- `parity:perf --baseline-lsg <binary>` also times a whole-garden build with another `lsg`, such as one built before a feature, and marks a slowdown above `[code]` `build_slowdown_pct`.
		- The `build-plugins` and `publication-speed` jobs in [`.github/workflows/ci.yml`](https://github.com/codekiln/logseq-gardener/blob/main/.github/workflows/ci.yml) run `parity:build-bench` and `parity:publish-bench --check` on a pinned encode garden commit.
	- ## Change the fixtures or budgets
		- Add a page title to `scripts/parity/fixtures.txt` when a comparison needs it; `Home` and `All pages` name Logseq's journals home and All pages routes.
		- Change `scripts/parity/budgets.toml` in the proposal of the feature that needs a different budget, with the measurements that justify it.
