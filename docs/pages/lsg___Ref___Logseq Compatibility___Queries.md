- # Queries Compatibility
	- `lsg` publishes each `{{query …}}` macro and `#+BEGIN_QUERY` block as Logseq's result box, with its header, result count, read-only clause row, results grouped by page, tables with Logseq's columns and sorting, collapsed queries and Logseq's error messages, and it evaluates every simple-query form a published Logseq site runs except `(between created-at …)`. It evaluates the queries while it builds the site, with the build date as today, so the browser runs no query and loads no graph. Datalog advanced queries, `:view` and `:result-transform` do not run, the `Setting properties` and refresh buttons are left out, and groups of pages other than journals are in page-name order.

	- Measured on 2026-10-27 against the `gh-pages` build of garden commit `083106d` (`gh-pages` `8132c95`, served locally, light theme, 1280×800, browser date 2026-10-27, time zone America/New_York) and an `lsg` build of the whole garden from `lsg` `48fcc54` (`mise run parity:build`, run `20261027T002614Z`). Because the garden has no query that returns results, the result, table, collapse and error states were measured on a copy of the `gh-pages` build in which the text of seven blocks on `Logseq/Queries` and `Logseq/Flavored Markdown` was replaced with test queries in `static/js/db.gz`. The blocks' references, properties and the rest of the graph were unchanged, so the results come from the garden's real data. The Fixture pages section lists the test queries and their measured results. The OpenSpec change [match-logseq-queries](https://github.com/codekiln/logseq-gardener/tree/main/openspec/changes/archive/2026-10-28-match-logseq-queries) then built queries, and [published-queries](https://github.com/codekiln/logseq-gardener/blob/main/openspec/specs/published-queries/spec.md) and [garden-queries](https://github.com/codekiln/logseq-gardener/blob/main/openspec/specs/garden-queries/spec.md) hold their requirements.
	- ## How the garden uses queries
		- The encode garden barely uses queries. Its pages and journals hold one `{{query}}` macro, and that one is blank (`Logseq/Queries`), and no `#+BEGIN_QUERY` block.
		- Its `logseq/config.edn` defines two advanced queries that Logseq adds under today's journal (`🔨 NOW` and `📅 NEXT`). Logseq shows them only when the reader's date has a journal page, so they were not visible when measured.
		- The query language matters more through flashcards: 37 `{{cards …}}` macros select their cards with the same simple-query language, using page references, `and`, `or` and `not`. [[lsg/Ref/Logseq Compatibility/Flashcards]] compares the decks, which use the same evaluator.
	- ## What Logseq's published site shows
		- Logseq renders a `{{query …}}` macro or a `#+BEGIN_QUERY` block as a live result box: a header with a title, a result count and view controls, then the matching blocks grouped by page, or a table. It evaluates every query in the reader's browser, against the whole graph, after the whole graph has loaded.
		- Source links point at the local `logseq/og` checkout, `6e7afa8eb` (`frontend` = `src/main/frontend`, `QC` = `frontend/components/query.cljs`). Measured live values come first and win where they differ from the checkout or from [[lsg/Ref/Logseq Published Site/Clickable Prototype]].
		- The prototype board differs from the live build in these places:
			- Its header is a 14px muted row with `2px 0 4px` padding; the live header is a 12px box with padding, a background and a ring.
			- It shows a collapsed query's count in parentheses; Logseq does not run a collapsed query, so it has no count to show.
			- It hides the tools of a collapsed advanced query; the live build shows them.
			- Its tables have only `block` and `page` columns, with `—` for dates; the live build adds property columns and fills the dates.
			- It has one error form, `Query failed:`; the live build has three.
			- It omits the query builder row that the live build shows under every simple query.

			- Keys: `:title`, `:query`, `:inputs`, `:rules`, `:result-transform`, `:view`, `:collapsed?`, `:group-by-page?`, `:remove-block-children?`, `:breadcrumb-show?`, `:table-view?` ([Advanced Queries](https://github.com/logseq/docs/blob/628cdde/pages/Advanced%20Queries.md)).

		- ### Performance in Logseq
			- The published app loads the whole database into the browser before it renders a page ([`publishing.cljs`](https://github.com/logseq/og/blob/6e7afa8eb/src/main/frontend/publishing.cljs#L50-L53)). On `Logseq/Queries` that is 22.6 MB of data and 8.1 MB of script before the title: 19,760 ms to the title on the desktop profile and 185,344 ms on the phone profile, with a peak JS heap near 1,970 MB ([[lsg/Ref/Logseq Compatibility/Performance]]).
			- After that, each query is fast. None of the measured queries took more than 50 ms, the point at which Logseq shows its refresh button. That includes the 603-block tmux query and a case-sensitive text search over every block.
			- Logseq caches each result and re-runs every query after each change to the database, unless the query's last run took more than 80 ms ([`react.cljs`](https://github.com/logseq/og/blob/6e7afa8eb/src/main/frontend/db/react.cljs#L298-L361)). In a published site, nothing changes the database except the reader's in-memory edits.
			- Result lists mount as they scroll into view, but tables draw every row.
	- ## What lsg publishes
		- **Evaluation:** the SDK's `query` module parses the simple language of `{{query …}}`, with the macro's arguments joined by `, `, and the EDN map of a `#+BEGIN_QUERY` block, after expanding `<% today %>`, `<% yesterday %>` and `<% tomorrow %>`. It evaluates the query over the reference index of selected visible pages while the site is built, so the browser runs no query. The publisher, the CLI, the language server and the flashcard decks share the same evaluator.
		- **Forms:** `[[page]]` and `#tag` match blocks whose path references include the page or an alias; `and`, `or` and `not` combine; `"text"` matches block source, case-sensitive; a bare word matches nothing, as in a published Logseq site; `task`, `todo`, `priority`, `between`, `property` and `page` match blocks; `page-property`, `page-tags`, `all-page-tags` and `namespace` return pages; `sort-by` orders the results; and `sample` keeps N results chosen by a generator seeded with the query's block id, so two builds of one commit agree. A query whose forms all return pages returns pages. Any other form, such as `(between created-at …)`, shows `Query failed:` naming the form.
		- **Today:** relative dates and the default journal queries use the build date that the journals feed uses, the UTC date of `SOURCE_DATE_EPOCH` when it is set and of the system clock otherwise.
		- **Header:** each query renders `div.custom-query` with the `.th` header in Logseq's measured styles. A simple query's title is the search icon and `Live query`, or `Live query for pages`; an advanced query's `:title` renders as 16px text, or as the named element with escaped text for a vector such as `[:h3 "…"]`. `N results` or `1 result` shows only above zero, counting blocks for grouped results. A simple query shows its parsed clauses in a read-only `.query-builder` row, such as `( AND [[yazi]] [[card]] )`.
		- **List view:** the query's own block is left out, and so is any result whose parent is also a result, unless `:remove-block-children? false`. Block results are grouped by page unless the map sets `:group-by-page? false`, the query contains `(by-page false)` or the map has a `:result-transform`: journals first, newest first, then the other pages by page name. Each `.custom-query-page-result` group has Logseq's measured styles, a fold control and the page title link, then each result's breadcrumb and the block with its children, rendered as embedded blocks are. A `{{query}}` inside a result shows as its literal text. A query with no results shows `No matched result`, and a blank query shows only its header.
		- **Table view:** a query renders a table when its block has `query-table:: true`, its map sets `:table-view? true`, its simple text ends with the word `table`, or it returns pages. Block tables have the columns `block`, `page`, then each non-built-in property on the results; page tables `page`, the page properties, `created-at` and `updated-at`. `query-properties` chooses and orders the columns, rows sort by `query-sort-by` (default `updated-at`) descending unless `query-sort-desc:: false`, and dates are the page file's git dates in `yyyy-MM-dd HH:mm`, UTC. Clicking a column title sorts by it and a second click reverses it. The table and list toggle appears where Logseq draws it and loads the other view from a fragment on click. Tables use the All pages table styles.
		- **Collapsed and large results:** a query with `:collapsed? true`, or on a block with `collapsed:: true`, renders closed with its title and buttons and no count, and loads its results and count when opened. Each query's in-page part holds whole groups or table rows up to 30 KB gzip; the rest sits in fragments of at most 100 KB gzip that load as the reader scrolls near the end.
		- **Errors:** a simple query that does not parse replaces the box with a bordered block error headed `Query Error:` above the query text. An advanced map that does not read shows the same box headed `Invalid query:`. A query that parses but cannot run, including an unsupported form, a Datalog `:query`, `:inputs` or `:rules`, keeps the header and shows `Query failed:` with the message. A map with a `:view` shows `Custom view failed:`, and a map with a `:result-transform` shows its untransformed results. Each case is also a build diagnostic with its page and line.
		- **References:** page references inside `#+BEGIN_QUERY` text and `{{query …}}` arguments are not references, as in Logseq.
		- **Default journal queries:** each `:default-queries :journals` entry in the simple language renders under the build date's journal on the journals feed and on that journal's page, when that journal is published and the query has results, and runs while collapsed with its count. Entries with a Datalog `:query`, such as both of the encode garden's, are skipped with one diagnostic each.
		- **Loading:** `lsg-queries.js` and `lsg-queries.css` are linked only from pages with a query; other pages are unchanged. Shift-click on a result's bullet adds a card for its block to the right sidebar, as in Logseq.
		- **Results on the encode garden:** measured on 2026-10-28 against Logseq's `gh-pages` build `8132c95` of garden commit `083106d`, the test queries in the Fixture pages section returned Logseq's counts, and `{{query [[tmux]]}}` started with Logseq's groups `2026-09-19 Sat`, `2026-09-15 Tue`, `2026-09-11 Fri`. `(between -30d today)` found 75 blocks against Logseq's 76, because a heading line without a bullet on `2026-10-14 Wed` merged into the block above; the OpenSpec change [split-unbulleted-headings](https://github.com/codekiln/logseq-gardener/tree/main/openspec/changes/archive/2026-10-28-split-unbulleted-headings) then made such a line a block of its own.
	- ## Performance
		- The `[queries]` table of [`scripts/parity/budgets.toml`](https://github.com/codekiln/logseq-gardener/blob/main/scripts/parity/budgets.toml) holds the budgets: `lsg-queries.js` at most 2 KB uncompressed, `lsg-queries.css` at most 1 KB gzip, each query's in-page part at most 30 KB gzip, each fragment at most 100 KB gzip, the collapsed tmux query showing its first group within 300 ms on desktop and 1,500 ms on the phone profile, a phone heap of at most 20 MB after all its fragments load, and a whole-garden build at most 10% slower than the `--baseline-lsg` binary. The fixture page with the tmux query stays within the `[desktop]` and `[phone]` first-paint budgets and does not grow when the fixture garden gains 2,000 pages.
		- On 2026-10-28, `parity:budgets` measured `lsg-queries.js` at 1,960 bytes and `lsg-queries.css` at 581 bytes gzip. On the whole garden, `Parity/Queries`, with nine query boxes, was 46.8 KB gzip, and the largest query fragment 49.9 KB gzip.
		- [[lsg/Ref/Logseq Compatibility/Performance]] records `Parity/Queries` with its title at 121 ms on desktop and 374 ms on the phone profile, with 57,390 bytes of data and 12,392 bytes of script before it; opening the collapsed tmux query in 20 ms and 618 ms; 568 groups after scrolling; a heap of 1.2 MB after every fragment; and a whole-garden build of 14.48 s against 14.25 s for the baseline binary (+1.6%).
	- ## Differences from Logseq
		- Queries are evaluated while the site is built. Logseq evaluates them in the reader's browser after loading the whole graph: 19.8 s on the desktop profile and 185 s on the phone profile for `Logseq/Queries`.
		- "Today" is the build date, so results with relative dates are as fresh as the last build. Logseq uses the reader's clock.
		- Datalog advanced queries show `Query failed:` with a message that the build evaluates simple queries only, and report a diagnostic. The garden's pages hold no Datalog query; its two default journal queries are Datalog, and Logseq shows those only to readers on a date with a journal.
		- A `:view` shows `Custom view failed:` and a `:result-transform` is ignored, which is how Logseq behaves when those functions fail. Running ClojureScript at build time would need an interpreter.
		- `(between created-at …)` is unsupported: in a published Logseq build its dates are only file-parse times.
		- The `Setting properties` dialog, the refresh button and the clause row's `+` button are left out, since no choice made there can be kept and no query runs slowly in the browser. The `report issue` link in the `Query Error:` box is left out, since it links to Logseq's tracker.
		- Groups of pages other than journals are in page-name order. Logseq uses the order of its database, which no build can reproduce.
		- `sample` chooses with a generator seeded by the query's block id. Logseq chooses again on every visit.
		- Table dates are the page file's git dates in UTC. Logseq shows the times its build parsed each file, in the reader's time zone.
		- Large results put the first part in the page and the rest in fragments. Logseq draws all 603 rows of the tmux table at once.
		- Scheduled and deadline lists under today's journal are a separate journal feature.
		- Logseq's dark-theme values were not measured; the box uses `lsg`'s theme tokens.
	- ## Before the change
		- The `lsg` build measured on 2026-10-27, from `48fcc54`, rendered queries from `crates/logseq-gardener-sdk/src/site/render.rs`, checked against the whole-garden build and a three-page test garden built with the same `lsg`. It evaluated no query.
